- 주의사항: [PII, 노이즈, 엣지 케이스 존재 여부 등]

## 3. 아키텍처 원칙 (Architecture Principles)
- 이 프로젝트는 다음 원칙을 따른다:
  1. 판단 로직과 실행 로직을 분리한다 (classify → decide → act 파이프라인)
  2. 모든 판단에는 근거(evidence/citation)를 남긴다 — 근거 없는 답변 금지
  3. 실패 시 안전한 기본값(escalate to human 등)으로 fallback 한다
  4. 프롬프트 인젝션/탈옥 시도로 의심되는 입력은 별도 플래그 처리 후 사람에게 넘긴다
  5. 단일 LLM 호출이 곧 아키텍처가 되지 않도록 한다 — 입력 로드/정규화, 컨텍스트 구성, 모델 호출, 응답 파싱, 스키마 검증, 라벨 강제, 재시도, 로깅, flag 여부 결정을 각각 별도 책임으로 분리

## 4. 입력 하나 끝까지 따라가기 체크리스트 (Trace-One-Input Self-Check)
> 시스템을 설명하기 전에, 입력 하나를 골라서 아래 질문에 답할 수 있는지 확인한다.
- [ ] 어디서 읽히는가?
- [ ] 어떻게 정제(clean)되는가?
- [ ] 어떤 컨텍스트가 추가되는가?
- [ ] 모델은 어디서 호출되는가?
- [ ] 어떤 스키마로 응답을 받는가?
- [ ] 응답 이후 코드는 무엇을 검증하는가?
- [ ] 무엇이 로깅되는가?
- [ ] 언제 재시도/보류(abstain)/리뷰 요청으로 넘어가는가?
- [ ] 최종 출력은 어디에 쓰이는가?

## 5. 폴더 구조 (Repo Layout)
```
code/           # 실제 에이전트 코드
data/           # 입력 데이터 (제출 시 제외 대상일 수 있음, 규칙 확인)
eval/           # 평가 하네스 및 테스트 케이스
output/         # 최종 예측 결과물 (output.csv 등)
transcripts/    # AI 채팅 로그 (log.txt)
```
- 파일명에 `helper`, `final`, `utils`, `test2` 같은 이름 쓰지 않기 — 역할이 드러나는 이름 사용
